## 2. Secrets

`/opt/chains-tcg/.env`, **mode 600, root-owned**, generated with `openssl` on
the server. It was never copied from a laptop and is not in git.

Generated fresh: `JWT_SECRET`, `POSTGRES_PASSWORD`, `MATCH_RESULT_HMAC_SECRET`,
`BOOSTER_PACK_SEED_SECRET`, `RPC_PROXY_INTERNAL_TOKEN`, `WAGER_ESCROW_KEYPAIR`,
`BOOSTER_TREASURY_KEYPAIR`.

Production values that matter for correctness:

```
AUTH_DOMAIN=ocva.online
AUTH_URI=https://ocva.online
ALLOWED_ORIGINS=https://ocva.online,https://www.ocva.online
```

`AUTH_DOMAIN` is what a wallet displays and what binds a signature to this
deployment. It is deliberately **not** `localhost` — a signature minted for one
domain must not verify against another. `ALLOWED_ORIGINS` contains the two
production web origins and **nothing else**; `http://localhost:5173` was
deliberately **not** added, so a developer's local frontend cannot talk to
production from a browser. (Add it only if you accept widening CORS on a
public host; server-to-server callers and curl are unaffected by CORS.)

### ⚠ Placeholder wager keypairs — NO REAL MONEY

`WAGER_ESCROW_KEYPAIR` and `BOOSTER_TREASURY_KEYPAIR` are **throwaway keys
generated by `openssl rand` on this server purely to satisfy the H-4 boot

## 3. Redeploy

From the repo root on your machine (**never** ship `.env`, `node_modules`,
`.git` or build output — the server builds its own images):

```bash
rsync -az --delete \
  --exclude 'node_modules' --exclude '.env' --exclude '.env.local' \
  --exclude '.git' --exclude 'dist' --exclude '*.tsbuildinfo' \
  --exclude '*.log' --exclude '.DS_Store' --exclude 'scratch' \
  --exclude 'coverage' --exclude 'DEPLOY-NOTES.md' \
  new-backend/ root@167.233.212.65:/opt/chains-tcg/

ssh root@167.233.212.65 'cd /opt/chains-tcg && docker compose up -d --build'
```

`--exclude 'DEPLOY-NOTES.md'` matters: that file exists only on the server, and
`--delete` would otherwise remove it.

On 2 vCPU a full six-image build is memory-tight. If it OOMs, build one service
at a time (`/opt/chains-tcg/build.sh` does exactly this) rather than adding swap.

> **Rebuilding one service?** Restart the gateway afterwards — nginx resolves
> upstream IPs once at boot and a rebuilt container gets a new one:
> `docker compose up -d --build game && docker compose restart gateway`

Migrations run automatically: `migrate` is a one-shot job that must exit 0
before any service starts. It is checksummed and re-running is a no-op.

## 4. Logs and health

```bash
cd /opt/chains-tcg
docker compose ps                       # all should read (healthy)
docker compose logs -f gateway          # or auth | profile | game | wager | rpc-proxy
docker compose logs -f wager            # settlement worker: one line per pass
docker compose exec postgres psql -U chains -d chains

curl -s 127.0.0.1:8080/healthz                       # gateway
for p in 4001 4002 4003 4004 4005; do curl -s 127.0.0.1:$p/readyz; echo; done
```

`/healthz` and `/readyz` are intentionally **not** routed through the gateway;
they answer on each container's own loopback port.

Watch `match_result_sig_invalid` in the wager logs. Any non-zero rate means
either an attack or a broken HMAC contract, and should page someone.

## 5. Rollback

The images are the artifact; the database is not disposable.

```bash
cd /opt/chains-tcg
docker compose down                 # stop, KEEP volumes (data survives)
docker compose up -d                # bring the current images back

# roll code back:
#   revert locally, re-run the rsync + `up -d --build` in §3.
```

- `docker compose down` keeps volumes. **`docker compose down -v` destroys the
  database** (`chains-backend_postgres-data`) — that is how the stack is reset
  to pristine, and it is not a rollback.
- Migrations are forward-only. A bad migration is fixed with a new file, not by
  editing an applied one (the runner refuses a checksum mismatch).
- Run compose only from `/opt/chains-tcg`, so you never act on the other
  project's stack.

## 6. Caddy

`/etc/caddy/Caddyfile` — a timestamped backup was taken before editing
(`Caddyfile.bak.<epoch>`, the owner's existing convention) and only this block
was **appended**:

```
api.ocva.online {
	reverse_proxy 127.0.0.1:8080
}
```

Deliberately minimal: the internal nginx gateway already sets CSP, CORS, rate
limits and the 256 KB body cap, so duplicating any of it here would produce
conflicting or doubled headers.

Verified by capturing the raw upstream request rather than assuming: Caddy
sets `X-Forwarded-Proto` (which the gateway is configured to honour in place of
`$scheme`) and `X-Forwarded-For`, and passes `Connection: Upgrade` /
`Upgrade: websocket` / `Sec-WebSocket-Key` through untouched for `/socket.io/`.

```bash
caddy validate --config /etc/caddy/Caddyfile
systemctl reload caddy      # RELOAD, never restart — restart drops the other sites
```

### One change was required in `gateway/nginx.conf`

Putting nginx behind Caddy makes `$remote_addr` the Docker bridge address for
**every** request. All three `limit_req` zones and `limit_conn` key on
`$binary_remote_addr`, so without a fix the whole internet would have shared a
single bucket: 5 auth requests/minute and 64 concurrent connections *in total*,
and a trivial denial of service. The gateway now trusts `X-Forwarded-For` from
private/loopback peers only (`real_ip_recursive off`, so it takes the address
the terminator itself observed and a client-supplied value is never selected).
`TRUST_PROXY_HOPS` stays `1` and remains correct.

## 7. ⚠ DNS — the one thing still outstanding

`api.ocva.online` currently resolves to **Porkbun parking**
(`pixie.porkbun.com`), not to this server. Until that changes Caddy cannot
issue a certificate, so **`https://api.ocva.online` does not serve yet.**

Create this record at the DNS provider for `ocva.online`:

| Type | Host / Name | Value | TTL |
|---|---|---|---|
| `A` | `api` | `167.233.212.65` | default (600) |

Nothing else is needed. Caddy has the site loaded already and will obtain the
certificate automatically within seconds of the record propagating. Confirm:

```bash
dig +short api.ocva.online            # expect 167.233.212.65
curl -sI https://api.ocva.online/healthz
ssh root@167.233.212.65 'journalctl -u caddy -n 40 --no-pager'   # cert issuance
```

If the web app is also to be served from this host, `ocva.online` and
`www.ocva.online` need their own records and their own Caddy blocks; today
those are expected to point at the frontend host (e.g. Vercel).

## 8. Frontend (Vercel)

The API is a **different origin** from the web app, so every browser call is
cross-origin. That is already handled: the gateway's `ALLOWED_ORIGINS` names
`https://ocva.online` and `https://www.ocva.online` exactly.

Set in the Vercel project (Production scope):

```
VITE_API_BASE=https://api.ocva.online
```

and for local development, in `.env.development`:

```
VITE_API_BASE=http://localhost:8080
```

**No secret from `/opt/chains-tcg/.env` belongs in Vercel.** Anything in a
`VITE_*` variable is compiled into the browser bundle and is public. In
particular there is no RPC key in the frontend any more (audit finding H-5) —
the browser calls `${VITE_API_BASE}/rpc/evm` and the key stays server-side.

Two constraints that will bite otherwise:

1. Point the custom domain `ocva.online` (and `www`) at Vercel, and `api` at
   this server (§7). They are separate records.
2. The gateway's CSP is `default-src 'self'; script-src 'self'` with **no**
   third-party hosts. `@google/model-viewer` from jsDelivr, Google Fonts and
   PeerJS will be blocked and must be self-hosted or dropped. This applies to
   pages served through this gateway; a Vercel-hosted frontend sends its own
   CSP, but keeping them consistent avoids surprises.

Tokens go in the `Authorization: Bearer` header, never cookies — there is no
shared cookie domain between `ocva.online` and `api.ocva.online`.

## 9. Reboot behaviour

Every long-running container is `restart: unless-stopped`; `migrate` is
`restart: "no"` because it is a one-shot job. `docker`, `containerd` and
`caddy` are all `systemd enabled`. No systemd unit was added — Compose's own
restart policy is the single mechanism, and a unit would fight it.

Verified: with the stack running, stopping Postgres and starting it again
brings all eight containers back to `(healthy)` within ~10s **with no manual
intervention** — which is the property an unordered boot depends on, since
Docker starts everything at once and `depends_on` does not apply at boot.

**Know this gotcha:** `unless-stopped` means *explicitly stopped stays
stopped*. After `docker compose down`, `stop`, or `kill`, the stack will **not**
come back on reboot until someone runs `docker compose up -d`. If you stop it
deliberately, either start it again or remember it will stay down.

A real host reboot was **not** performed — this server is shared with a live
project and rebooting it was not ours to do.
